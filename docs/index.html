Motivation

The Problem & The Solution

⚠The Problem

People with insulin-dependent diabetes must estimate the carbohydrates in every meal to calculate their insulin dose. Manual carb counting is slow, error-prone, and requires constant guesswork about portion sizes — and dosing errors have real health consequences.

✓The Solution

InsuScan replaces guesswork with measurement. The user photographs their plate; the system detects each food item, measures its real-world size using a physical reference object, estimates weight and carbohydrates, and returns a personalised insulin dose based on the user's own insulin plan.

System Design

System Architecture

InsuScan is a full-stack platform: a native Android client, a Spring Boot backend with a layered architecture, a Python segmentation microservice, and external AI and data services.

📱Android Client

Native Kotlin app. Captures top-view and side-view meal photos with CameraX, collects optional ARCore depth data, manages personal insulin plans, and signs in with Firebase Authentication.

⚙Spring Boot Server

Java 21 REST API. Runs the food-estimation pipeline, manages users and meal records, calculates insulin doses, and exposes interactive API docs via Swagger UI.

✂SAM Service

Python microservice running Segment Anything. Produces a precise pixel mask for every food item on the plate, plus depth estimation for height measurement.

🤖Google Gemini

Vision-language model used for semantic tasks: identifying what each segmented food item actually is.

🥗USDA FoodData Central

Official nutrition database. Provides carbohydrates and macronutrients per 100g for every identified food, plus density data for weight estimation.

🔥Firebase Firestore

Cloud database storing user profiles, insulin settings, and complete meal records with their calculation results.

Core Technology

The 11-Stage Food Estimation Pipeline

The heart of InsuScan. A single scan request travels through eleven ordered stages, each transforming raw pixels into physical measurements — ending with grams of carbohydrates per food item.

1

Calibration

Detects a physical reference object (insulin pen or credit card) to establish the pixel-to-centimeter scale.

2

Plate Geometry

Locates the plate and measures its bounding box and diameter.

3

SAM Segmentation

Generates a precise segmentation mask for each food item on the plate.

4

Perspective Correction

Rectifies the top-view image so pixel areas are geometrically accurate.

5

Food Detection

Gemini identifies the food class of every segmented item.

6

Food Area

Converts each item's pixel area into real-world area in cm².

7

ARCore Depth Fusion

Fuses ARCore point-cloud data from the device when available.

8

Food Height

Estimates each item's height in centimeters from the side-view image.

9

Volume Calculation

Combines area and height into an estimated volume in cm³.

10

Nutrition & Density

Looks up USDA nutrition and density data to convert volume into weight and carbohydrates.

11

Sanity Check

Plausibility gate that aggregates per-stage confidence into a final score.

FATAL FAILUREThe pipeline stops immediately and a clear error is returned to the client.
DEGRADED FAILUREThe pipeline continues with reduced confidence and a warning attached to the response.
Safety First

Personalised Insulin Dosing

Carb estimation is only half the job. The server calculates the recommended dose using each user's own medical parameters, and validation runs on both client and server.

📋Insulin Plans

Each user defines one or more insulin plans — ICR (insulin-to-carb ratio), ISF (correction factor), and target glucose. Plans are validated before saving; incomplete plans are blocked.

🧮Dose Calculation

The server is the single source of truth: it computes a carb dose from total carbohydrates and an optional correction dose from the current blood-glucose reading.

🛡Validation & Testing

Structured exception handling, input validation on both sides, and automated JUnit test suites covering calculation edge cases on client and server.
