Core Endpoint

Vision Pipeline — /vision/v2

The main endpoint that receives meal photos and returns food items with carbohydrate estimates and a recommended insulin dose.

POST /vision/v2/scan Analyse food images → return meal + insulin dose

Multipart Parameters

ParameterTypeRequiredDescription
topFilefile✅Top-view photo of the meal
sideFilefile✅Side-view photo of the meal
referenceObjectTypequery✅Reference object type: INSULIN_SYRINGE, CARD, or NONE
emailquery✅User email for profile lookup
arcoreDataquery❌Serialised ARCore depth JSON (when available)
topImageWidthquery❌Sensor width in pixels
topImageHeightquery❌Sensor height in pixels

The response is a MealBoundary containing all detected food items, their estimated weights and carbs, a confidence score, an insulin calculation result, and any pipeline warnings. See the Data Models section below.

User Management

Users — /users

POST /users Register a new user
GET /users/login/{systemId}/{email} Authenticate / retrieve user
GET /users/{systemId}/{email} Get user profile by ID
GET /users/by-email?systemId=&email= Look up user by email (query param)
PUT /users/{systemId}/{email} Update user profile
DEL /users/{systemId}/{email} Delete user account
GET /users/{systemId}/{email}/medical-complete Check if medical profile is complete
Meal Lifecycle

Meals — /meals

Meals follow a three-state lifecycle. The scan endpoint creates a meal in PENDING state; the user reviews, optionally edits food items, then confirms; finally the meal is marked complete.

PENDING
scan creates meal
→
CONFIRMED
user accepts + logs dose
→
COMPLETED
meal finalised
POST /meals/{systemId}/{email} Create a new meal record
POST /meals/{systemId}/{email}/save-scanned Save a scanned meal with food items
GET /meals/{systemId}/{mealId} Get meal by ID
GET /meals/user/{systemId}/{email} List user's meals (paginated)
GET /meals/recent/{systemId}/{email}?count=5 Get N most recent meals
GET /meals/user/{systemId}/{email}/by-date?from=&to= Filter meals by date range
GET /meals/count/{systemId}/{email} Get total meal count for user
PUT /meals/{systemId}/{mealId}/fooditems Update food items (user edits)
PUT /meals/{systemId}/{mealId}/confirm Confirm meal — log actual dose & glucose
PUT /meals/{systemId}/{mealId}/complete Mark meal as completed
PUT /meals/{systemId}/{mealId}/portion Update portion analysis data
DEL /meals/{systemId}/{mealId} Delete meal
Supporting Endpoints

Food Search & Insulin

Food — /food

GET /food/search?query=&limit=

Search USDA FoodData Central database by keyword.

POST /food/ai-search

AI-enhanced semantic food search using Gemini for fuzzy matching.

Insulin — /insulin

POST /insulin/calculate

Calculate a personalised insulin dose given carbs and user profile. See the Dosing page for the full formula.

Admin — /insuscan/admin

GET /insuscan/admin/users List all users (paginated)
DEL /insuscan/admin/users Delete all users
DEL /insuscan/admin/meals Delete all meals

Meal Statuses

PENDING
Created by scan
→
CONFIRMED
User reviewed & accepted
→
COMPLETED
Finalised
PENDING MEALS FILTERED FROM HISTORY When the client fetches the user's meal history, meals with status PENDING are filtered out server-side. This prevents abandoned or in-progress scans from appearing in the history list.
