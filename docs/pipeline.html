Core Technology

The 11-Stage Pipeline

A deep dive into how InsuScan transforms raw meal photographs into per-item weight, carbohydrates, and confidence scores.

Overview

How It Works

The pipeline is triggered by a single POST /vision/v2/scan request carrying a top-view image, a side-view image, the user's chosen reference object type, and optional ARCore depth data. All eleven stages run in strict order inside a shared PipelineContext — each stage reads what it needs and writes its own outputs, never reading outputs from a later stage.

DESIGN PRINCIPLE — ERROR PROPAGATION Calibration errors in Stage 1 propagate multiplicatively through the rest of the pipeline. An error in the pixel-to-cm ratio is squared when computing area (cm²) and approximately cubed when computing volume (cm³). This makes Stage 1 the single highest-leverage point in the entire system.
FATAL FAILURE Pipeline stops immediately. A clear error message is returned to the client. Example: no food detected at all.
DEGRADED FAILURE Pipeline continues with reduced confidence. A warning is attached to the response so the user knows accuracy may be lower. Example: reference object not found — falling back to plate size estimate.
Stages 1–2

Calibration & Plate Geometry

1

Calibration — Reference Object Detection

Establishes the pixel-to-centimeter scale for both images

The user places a physical object of known dimensions next to their plate. The system currently supports two reference object types: an insulin pen (16.0 cm × 1.25 cm) and a credit card / ID card (8.56 cm × 5.398 cm). A third option, "None," skips reference detection and falls back to a plate-size estimate — which is the lowest-accuracy path.

Detection runs in a CV-first, Gemini-fallback order. The server first attempts to detect the reference object using OpenCV with a strategy pattern — CardReferenceStrategy evaluates aspect ratio, rectangularity, and optionally a homography estimate; the pen strategy uses contour-based fragment clustering. If the CV detector succeeds with confidence above a configurable threshold, its result is used directly. If it fails or its confidence is too low, Gemini Vision is called to locate the object and provide a bounding box.

When both CV and Gemini succeed, their pixel-to-cm ratios are cross-checked. If they disagree by more than a configured gap, the CV result is rejected and Gemini's ratio is used, since CV detection can be fooled by similar-looking objects in the frame.

3-TIER FALLBACK CHAIN If the primary object is not detected, the system checks whether an alternative reference object was found (e.g., the user selected "pen" but a card is visible). If that also fails, calibration falls back to a standard plate size estimate — a 700-pixel approximation that allows the pipeline to continue in DEGRADED mode.

The output of this stage is a pixelToCmRatio for each image (top and side), plus the bounding box coordinates of the detected reference object.

2

Plate Geometry

Locates the plate and measures its real-world diameter

With the pixel-to-cm ratio established, this stage detects the plate's bounding box and circle in the top image. The plate's real-world diameter is computed by converting the pixel measurements using the calibration ratio. Gemini provides a visual estimate of the plate dimensions, but when both images fell back to the plate-size estimate in Stage 1 (meaning no reference object was found at all), the standard plate configuration overrides Gemini's estimate to prevent compounding inaccuracies.

The plate geometry (center, radius, bounding box) serves as a spatial anchor for all subsequent stages: SAM masks are clipped to the plate boundary, food area percentages are computed relative to the plate area, and volume sanity checks compare against the plate's estimated container volume.

Stages 3–5

Segmentation & Food Detection

3

SAM Segmentation

Pixel-accurate masks for every food item on the plate

The Python SAM microservice (running MobileSAM with the vit_t architecture) receives the top-view image along with bounding boxes for each food item (initially estimated by Gemini). For each bounding box, SAM generates a binary mask — the exact set of pixels belonging to that food item.

If a plate circle was detected in Stage 2, every mask is clipped to the plate boundary (logical AND with the plate mask). This prevents food pixels outside the plate from inflating area estimates.

When multiple food items overlap, an exclusive assignment step resolves conflicts: overlapping pixels are assigned to the item whose SAM confidence score is highest, ensuring each pixel is counted exactly once. The output is a maskPixelCount and a samMaskScore per item.

SIDE-VIEW SEGMENTATION SAM also runs on the side-view image. For each item's side bounding box, it produces a mask and measures the vertical pixel extent (top row to bottom row), converting it to centimeters using the side-image calibration ratio. This height measurement is later fused with Gemini's estimate.
4

Perspective Correction

Rectifies the top-view for geometrically accurate area measurement

Even when the user holds the phone approximately flat, slight tilt introduces perspective distortion — a circle appears as an ellipse, and area measurements become biased. This stage applies a geometric correction to ensure pixel areas in the top-view image correspond to true real-world areas.

5

Food Detection

Gemini identifies what each segmented item actually is

This is where AI handles semantics. Gemini Vision receives the top-view image along with instructions about the reference object and container type, and returns a structured JSON response identifying every food item. For each item, Gemini provides: a visual name (e.g., "Grilled Chicken Breast"), a base ingredient (e.g., "chicken"), a confidence score, USDA search terms, the food's visual state (RAW, COOKED, FRIED, etc.), texture type (SOLID, GRANULAR, LEAFY, MIXED), a height category, a coverage percentage, and a bounding box.

DESIGN DECISION — SEPARATION OF CONCERNS Gemini handles semantics (what is this food?); OpenCV, SAM, and ARCore handle measurement (how big is it?). The vision-language model is not asked to measure physical dimensions — it is unreliable for precise geometric tasks. Instead, its bounding boxes serve as prompts for SAM, and its coverage percentages serve as cross-checks against the mask-based area.
Stages 6–8

Measurement — Area, Depth & Height

6

Food Area

Per-item pixel area → real-world area in cm²

Each item's mask pixel count from Stage 3 is converted to square centimeters using the calibration ratio from Stage 1. A coverage percentage (item area / plate area × 100) is also computed. If SAM segmentation was successful, it is the primary area source; Gemini's coverage_percent estimate is used as a cross-check and fallback.

If the total food area exceeds the plate area, a high-severity warning is emitted — this usually signals a calibration or segmentation error.

7

ARCore Depth Fusion

Fuses device depth data when available

When the Android client has ARCore support and the device hardware allows it, a depth point cloud is captured alongside the meal photo. This stage fuses the ARCore depth data into the pipeline context, providing an additional per-pixel depth signal that can improve height estimation accuracy.

ARCore is declared as optional in the Android manifest — the app runs without it on devices that don't support it, and the pipeline gracefully skips this stage when no depth data is provided.

8

Food Height

Estimating how tall each food item is, in centimeters

Height estimation fuses two independent signals: Gemini's effective height estimate (which accounts for the food's "effective" cylindrical height — a dome of rice is not the same as a flat steak, even at the same tallest point) and SAM's pixel-based measurement from the side-view mask (raw vertical extent converted to cm).

The fusion logic follows a preference order: when both sources agree (within a configurable ratio threshold), a high-confidence fused estimate is produced. When they disagree, Gemini's estimate is preferred because it captures effective height rather than raw pixel extent. When only one source produced a result, that source is used with reduced confidence. If both report zero, a fallback of 1.0 cm is applied with very low confidence.

MONOCULAR DEPTH ESTIMATION The SAM service also runs Depth-Anything-V2-Small, a monocular depth estimation model. Its /depth_items endpoint computes a per-item depth signal using a ring-baseline approach: for each food item, the median depth inside the mask is compared to the median depth in a ring of pixels surrounding the mask (excluding other food items). The difference — the "protrusion" — represents how much the food rises above the plate surface.
Stages 9–11

Volume, Nutrition & Sanity Check

9

Volume Calculation

Area × Height → cm³

Each item's real-world area (cm²) is multiplied by its effective height (cm) to produce a volume estimate in cubic centimeters. An effectiveDensityFactor from Gemini (0.3–1.0) is applied to account for void space — bread is roughly 0.65 (35% air), leafy salad is about 0.35, and solid chicken is close to 1.0.

If the total volume across all items exceeds the plate's estimated container volume, a high-severity warning is raised.

10

Nutrition & Density Lookup

USDA database → macronutrients and density per item

For each identified food item, the USDA FoodData Central API is queried using the search terms provided by Gemini. The response provides carbohydrates, protein, fat, fiber, and water content per 100 g. A density value (g/cm³) is derived from the nutrient profile and texture type, enabling the conversion from volume to weight: weightG = volumeCm3 × densityGPerCm3.

If a food is not found in the USDA database, a high-severity warning is raised and manual weight input is required from the user.

From the weight and the per-100g nutrient data, the system computes per-item carbs, protein, fat, and fiber in grams. A netCarbsG field (carbs minus fiber) represents the carbohydrates that actually impact blood sugar.

11

Sanity Check

Plausibility gate and final confidence aggregation

The final stage reviews the full set of results for plausibility. Per-item weight is checked against a plausible range (3 g – 500 g); weights outside this range trigger a warning. Per-stage confidence scores — from calibration, segmentation, area, height, and nutrition — are aggregated into a single final confidence score that accompanies the response.

The complete result is returned to the client as a MealBoundary containing: every food item with its name, estimated weight, carbs, and confidence; meal totals; and a list of any warnings generated along the way.
