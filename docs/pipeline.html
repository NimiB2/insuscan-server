Core Technology

The 11-Stage Pipeline

A deep dive into how InsuScan transforms raw meal photographs into per-item weight, carbohydrates, and confidence scores.

Overview

How It Works

The pipeline is triggered by a single POST /vision/v2/scan request carrying a top-view image, a side-view image, the user's chosen reference object type, and optional ARCore depth data. All eleven stages run in strict order inside a shared PipelineContext - each stage reads what it needs and writes its own outputs, never reading outputs from a later stage.

DESIGN PRINCIPLE - ERROR PROPAGATION Calibration errors in Stage 1 propagate multiplicatively through the rest of the pipeline. An error in the pixel-to-cm ratio is squared when computing area (cm²) and approximately cubed when computing volume (cm³). This makes Stage 1 the single highest-leverage point in the entire system.
FATAL FAILURE Raised only by Food Detection, when the vision model call itself fails (API error or rate limit). The pipeline stops immediately and an error is returned to the client. Calibration and Plate Geometry never fail fatally by design -both degrade to fallback values and continue.
DEGRADED FAILURE Pipeline continues with reduced confidence. A warning is attached to the response so the user knows accuracy may be lower. Example: reference object not found - falling back to plate size estimate.
Stages 1–2

Calibration & Plate Geometry

1

Calibration - Reference Object Detection

Establishes the pixel-to-centimeter scale for both images

The user places a physical object of known dimensions next to their plate. The system currently supports two reference object types: an insulin pen (16.0 cm × 2.0 cm) and a credit card / ID card (8.56 cm × 5.398 cm). A third option, "None," skips reference detection and falls back to a plate-size estimate - which is the lowest-accuracy path.

Detection runs in a CV-first, Gemini-fallback order. The server first attempts to detect the reference object using OpenCV with a strategy pattern - CardReferenceStrategy evaluates aspect ratio, rectangularity, and optionally a homography estimate. the pen strategy uses contour-based fragment clustering. If the CV detector succeeds with confidence above a configurable threshold, its result is used directly. If it fails or its confidence is too low, Gemini Vision is called to locate the object and provide a bounding box.

When both CV and Gemini succeed, their pixel-to-cm ratios are cross-checked. If they disagree by more than the configured gap (25%), the CV result is rejected. In the side image Gemini's ratio is then used. in the top image the ratio is discarded entirely and the stage falls back to deriving scale from the measured plate diameter, since an unverified bounding box is treated as untrustworthy for area measurement.

3-TIER FALLBACK CHAIN If the primary object is not detected, the system checks whether an alternative reference object was found (e.g., the user selected "pen" but a card is visible). If that also fails, calibration falls back to a standard plate size estimate - a 700-pixel approximation that allows the pipeline to continue in DEGRADED mode.

The output of this stage is a pixelToCmRatio for each image (top and side), plus the bounding box coordinates of the detected reference object.

2

Plate Geometry

Locates the plate and measures its real-world diameter

This stage runs two Gemini calls in parallel: one on the top image for the plate's diameter, container type and fill percentage, and one on the side image for its inner depth. When Stage 1 produced a pixel-to-cm ratio, the diameter is computed by converting the plate's pixel span using that ratio.

When no reference object was found, Gemini estimates the diameter directly from the image. If its confidence falls below 0.85, the value is snapped to the nearest standard plate size (18, 22 or 26 cm) rather than trusted as-is. The measured diameter is then used to derive the top-view pixel-to-cm ratio that Stage 1 could not produce.

The plate geometry (center, radius, diameter, depth) serves as a spatial anchor for the remaining stages: food area percentages are computed relative to the plate area, height estimates are compared against the plate's inner depth, and volume sanity checks compare against the plate's estimated container volume.

Stages 3–4

Perspective Correction & Food Detection

3

Perspective Correction

Rectifies the top-view for geometrically accurate area measurement

Even when the user holds the phone approximately flat, slight tilt introduces perspective distortion - a circle appears as an ellipse, and area measurements become biased. This stage applies a geometric correction to ensure pixel areas in the top-view image correspond to true real-world areas.

CURRENTLY DISABLED The stage is present in the pipeline but its skip threshold is set to 90°, so tilt estimation is bypassed and the top image passes through unmodified. It is documented here because it remains part of the pipeline's structure and is intended to be re-enabled.
4

Food Detection

Gemini identifies what is on the plate

This is where AI handles semantics. Gemini Vision receives the top-view image and returns a structured JSON response identifying every food item. For each item, Gemini provides: a visual name (e.g., "Grilled Chicken Breast"), a base ingredient for USDA lookup (e.g., "chicken"), a confidence score, 2–3 USDA search terms, the food's visual state (RAW, COOKED, FRIED, GRILLED, BAKED, BOILED), an effective_density_factor (0.3–1.0), a coverage_percent, and a bounding box.

DESIGN DECISION - SEPARATION OF CONCERNS Gemini handles semantics (what is this food?). OpenCV, SAM, and ARCore handle measurement (how big is it?). The vision-language model is not asked to measure physical dimensions - it is unreliable for precise geometric tasks. Instead, its bounding boxes serve as prompts for SAM, and its coverage percentages serve as cross-checks against the mask-based area.
Stages 5–7

Measurement - Area, Height & Volume

5

Food Area

Per-item pixel area → real-world area in cm²

Before the area is computed, the Python SAM microservice (running MobileSAM with the vit_t architecture) receives the top-view image along with Gemini's bounding boxes. For each bounding box, SAM generates a binary mask - the exact set of pixels belonging to that food item. When multiple items overlap, an exclusive assignment step resolves conflicts: overlapping pixels are assigned to the item whose SAM confidence score is highest, ensuring each pixel is counted exactly once. The output is a maskPixelCount and a samMaskScore per item.

Each item's mask pixel count is then converted to square centimeters using the calibration ratio from Stage 1, and a coverage percentage (item area / plate area × 100) is computed. If SAM segmentation succeeded it is the primary area source. otherwise the bounding box is used with a 0.75 shape-correction factor, and failing that, a share of the plate area. Gemini's coverage_percent serves purely as a cross-check - a disagreement above 1.5× lowers the item's area confidence by 30% but never replaces the measured area.

If the total food area exceeds the plate area, a high-severity warning is emitted and all item areas are proportionally normalized down to fit the plate - this usually signals a calibration or segmentation error.

6

Food Height

Estimating how tall each food item is, in centimeters

Height estimation fuses two independent signals: Gemini's effective height estimate (which accounts for the food's "effective" cylindrical height - a dome of rice is not the same as a flat steak, even at the same tallest point) and SAM's pixel-based measurement from the side-view mask. For each item's side bounding box, SAM produces a mask and measures its vertical pixel extent (top row to bottom row), converting it to centimeters using the side-image calibration ratio.

The fusion logic follows a preference order: when both sources agree (within a configurable ratio threshold), a high-confidence fused estimate is produced. When they disagree, Gemini's estimate is preferred because it captures effective height rather than raw pixel extent. When only one source produced a result, that source is used with reduced confidence. If both report zero, a fallback of 1.0 cm is applied with very low confidence.

ARCORE DEPTH FUSION When the Android client has ARCore support and the device hardware allows it, depth measurements are captured alongside the meal photo. This stage fuses the ARCore measurements - plate depth, plate diameter, and per-item heights - with the pipeline's own vision-based estimates. ARCore's weight in the weighted average scales with its reported confidence (0.70 / 0.50 / 0.25), so a high-confidence reading dominates while a low-confidence one acts as a minor correction. ARCore is declared as optional in the Android manifest - the app runs without it on devices that don't support it, and the fusion is skipped entirely when no depth data is provided.
7

Volume Calculation

Area × Height → cm³

Each item's real-world area (cm²) is multiplied by its effective height (cm) to produce a volume estimate in cubic centimeters. This stage is pure arithmetic - no AI and no heuristics are involved.

If the total volume across all items exceeds the plate's estimated container volume, a high-severity warning is raised.

Stages 8–11

Nutrition, Weight & Sanity Check

8

Nutrition & Density Lookup

USDA database → macronutrients and density per item

For each identified food item, the USDA FoodData Central API is queried using the search terms provided by Gemini. The response provides carbohydrates, protein, fat, fiber, and water content per 100 g. A density value (g/cm³) is derived from the nutrient profile and texture type, enabling the conversion from volume to weight: weightG = volumeCm3 × densityGPerCm3.

If a food is not found in the USDA database, a high-severity warning is raised and manual weight input is required from the user.

From the weight and the per-100g nutrient data, the system computes per-item carbs, protein, fat, and fiber in grams. A netCarbsG field (carbs minus fiber) represents the carbohydrates that actually impact blood sugar.

9

Weight

Volume × Density → grams

Each item's volume is multiplied by its density to produce a weight in grams: weightG = volumeCm3 × densityGPerCm3. Items whose calculated weight falls outside the plausible range of 3 g – 500 g trigger a warning for review. An item with no resolved density cannot be weighed and is carried forward without a weight value.

10

Aggregation

Per-item macronutrients → meal totals

From each item's weight and its per-100 g nutrient data, the system computes absolute carbs, protein, fat, and fiber in grams. A netCarbsG field (carbs minus fiber, floored at zero) represents the carbohydrates that actually impact blood sugar. All per-item values are then summed into meal-level totals, along with counts of how many items were found, how many were missing from USDA, and how many require user validation.

11

Sanity Check

Plausibility gate on the finished meal estimate

The final stage validates the meal as a whole: a total weight below 20 g or above 1500 g raises a warning, and the computed energy density is checked against the physical limit of pure fat (9 kcal/g) - exceeding it signals a mathematical impossibility in the nutrient data. Per-item weight plausibility (3 g – 500 g) is checked earlier, in Stage 9.

Confidence aggregation happens after the pipeline completes, when the response is assembled: per-stage confidence scores are combined into a single overall score, warning penalties are applied, and a safe-for-dosing flag is derived. The complete result is returned to the client as a MealBoundary containing: every food item with its name, estimated weight, carbs, and confidence. meal totals. and a list of any warnings generated along the way.
