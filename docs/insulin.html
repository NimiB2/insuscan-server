Safety & Accuracy

Personalised Insulin Dosing

How InsuScan calculates a recommended dose from carbohydrates, the user's insulin plan, and optional glucose correction — with validation at every step.

Core Formula

Dose Calculation

The server is the single source of truth for insulin dose calculation. The formula lives in InsulinCalculator.java and uses three parameters from the user's insulin plan.

INSULIN DOSE FORMULA

Carb Dose = Total Carbs (g) ÷ ICR (g/unit)
Correction Dose = (Current Glucose − Target Glucose) ÷ ISF
Total Dose = Carb Dose + Correction Dose   (floored at 0)

📋Parameter Definitions

ICR (Insulin-to-Carb Ratio) — grams of carbs covered by 1 unit of insulin. Stored as "1:X" (e.g., "1:10" means 1 unit covers 10 g). The system auto-normalises inverted values: if a user enters 0.1, it is corrected to 10.

ISF (Insulin Sensitivity Factor / Correction Factor) — how many mg/dL 1 unit of insulin lowers blood glucose.

Target Glucose — the user's desired blood glucose level in mg/dL.

💡Worked Example

A meal is scanned and estimated at 45 g carbs. The user's plan: ICR = 1:10, ISF = 50 mg/dL, target glucose = 100 mg/dL, current glucose = 180 mg/dL.

Carb dose = 45 ÷ 10 = 4.5 units

Correction dose = (180 − 100) ÷ 50 = 1.6 units

Total dose = 4.5 + 1.6 = 6.1 units

Server rounds to 2 decimals → 6.10 units. Client applies pen-step rounding (e.g., 0.5 u step) → 6.0 units.

Personalisation

Insulin Plans

Users can define multiple insulin plans for different situations. Each plan is a self-contained set of dosing parameters.

An InsulinPlan has five fields: a unique ID, a user-visible name (e.g., "Regular", "Sick Day", "Workout"), an isDefault flag, and the three dosing parameters — ICR, ISF, and target glucose. Plans are stored locally on the device via UserProfileManager and synced to Firestore through the server's User API.

The user selects an active plan from the home screen. When a scan completes, the active plan's parameters are used for dose calculation. If no plan is selected, the app throws InsulinException.NoActivePlan before the calculation is attempted.

🔄ICR Normalisation

The server's CalculationParams accepts ICR as a "1:X" string or a raw float. If the value is less than 1.0, it is treated as an inverted ratio (units/gram) and auto-corrected to grams/unit. This prevents a common input error from causing wildly wrong doses.

🚫Incomplete Profile Blocking

A plan must have all three parameters (ICR > 0, ISF > 0, target glucose > 0) to be considered complete. The PlanValidator checks this before saving — incomplete plans cannot be saved, and incomplete profiles cannot trigger a dose calculation.

📐Pen-Step Rounding

The server rounds the dose to 2 decimal places. The client applies the user's pen-step rounding (0.5 u or 1 u) via SummaryCalculationHelper.roundForPen(). This split ensures the server stays precise while the displayed dose matches what the user's pen can physically deliver.

Glucose Correction

Correction Dose Logic

The correction dose is optional — it is only calculated when the user provides their current blood glucose reading.

When current glucose is above the target, the correction dose is positive — it adds insulin to bring blood sugar down. When current glucose is below the target, the correction dose is negative — it subtracts from the carb dose to prevent a low. However, the total dose is floored at zero: InsuScan will never recommend a negative insulin dose.

If the user does not provide a glucose reading, the correction dose is simply 0 and only the carb dose is returned.

INCOMPLETE PROFILE HANDLING When a user's profile is missing one or more of ICR, ISF, or target glucose, the calculator falls back to built-in defaults and attaches a "Profile incomplete - using defaults" warning to the result. The missingFields list in the response tells the client exactly which parameters are missing.

DUAL-SIDE VALIDATION Input validation runs on both client and server independently. The client catches errors early (before a network call), and the server catches them again (for safety, and because the API can be called directly). Structured exception hierarchies — InsulinException on the client, GlobalExceptionHandler on the server — produce clear, user-facing error messages.
Dose Gate

The DoseGateEvaluator

Before presenting a recommended dose to the user, the server runs a gate evaluation that checks whether the calculation should proceed, proceed with a warning, or be blocked.

The gate evaluator uses the user's medical profile completeness and the calculated dose to produce a DoseGateDecision. This decision tells the client whether to show the dose normally, show it with a warning, or withhold it entirely — ensuring that even if the calculation succeeds, an unsafe result does not reach the user without appropriate context.

Quality Assurance

Automated Testing

Insulin calculations are covered by dedicated JUnit test suites on both client and server.

⚙Server Tests

InsulinCalculatorFullTest covers: standard calculations, decimal ratios (1:7.5), inverted ratio auto-correction, plan ratio overrides, fractional carbs, rounding to 2 decimals, zero carbs, high carbs exceeding warning thresholds, and glucose correction (positive and negative).

InsulinInvalidProfileTest covers edge cases: missing ICR, missing ISF, missing target glucose, and various combinations of incomplete profiles.

📱Client Tests

PlanValidatorTest covers: valid plans pass, missing ICR blocked, missing ISF blocked, missing target glucose blocked, zero values blocked, negative values blocked, and ICR values below 1.0 rejected (the client requires proper values; normalisation is the server's job).
